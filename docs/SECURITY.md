# CRI Security — Internal Only

## Current security posture

This is a pre-GitHub prototype, not a production security boundary. Sensitive API endpoints use a static bearer token supplied through environment variables (minimum 32 bytes); JWT/session, CSRF, rate limiting and multi-user RBAC are not implemented. The in-process Policy class is deny-by-default but is not an independent OPA authority. Audit is local JSONL with a SHA-256 hash chain; privileged host access can alter/delete the entire file. Kill is a file latch, not an independent watchdog. Approval tokens use HMAC, expiry and SQLite nonce replay prevention. Memory is in-process. Docker sandbox execution is fail-closed when Docker is absent, but runtime isolation has not been exercised in this environment.

## Threat model

Task code and proposals may be generated by an LLM and must be treated as untrusted. It may contain mistakes, prompt injection, malicious behavior or resource abuse. The project is personal, but lower likelihood of a targeted attacker does not replace technical controls.

The Docker command applies `--network=none`, `--read-only`, non-root UID, dropped capabilities, `no-new-privileges`, PID/CPU/memory limits, a read-only bind mount, temporary no-exec tmpfs and a hard timeout. These controls reduce network access, host write access and resource abuse. They do not eliminate kernel/runtime escapes, Docker daemon compromise, supply-chain risk, unsafe image provenance, host administrator access or misconfiguration. Docker alone is not a complete isolation boundary.

## Invariants

- Increased capability never implies increased authority.
- Child scopes are the intersection of parent scopes and child-role capabilities.
- Agents cannot issue human approval tokens through ToolGateway.
- No valid sandbox means no code execution and no promotion path.
- Agents do not receive shell, Docker socket or direct host filesystem tools.
- Audit hash-chain integrity is detectable, but local storage is not immutable against privileged host access.

## gVisor and Firecracker

Firecracker requires KVM and `/dev/kvm`; standard GitHub-hosted runners and free VPS plans do not guarantee these. gVisor requires a compatible installed runtime (`runsc`) and host configuration. Until tested on a dedicated self-hosted Linux runner, both remain future providers and Fail-Closed stays enabled.

## Upgrade path

1. Separate sandbox runner with machine authentication and no Docker socket in API.
2. External OPA policy authority with read-only policy bundles.
3. PostgreSQL audit plus append-only object storage/WORM retention.
4. Independent watchdog/kill controller outside agent/API process.
5. gVisor or Firecracker on a dedicated KVM host with proof tests.
