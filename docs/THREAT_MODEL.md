# CRI Threat Model — Internal

## Assets

Human approval authority, policy definitions, agent scopes, source code, secrets, audit history, sandbox host, workflow state, memory, and release artifacts.

## Trust boundaries

1. Human administrator versus API client.
2. Control plane versus agent runtime (not yet implemented as a separate process).
3. API versus sandbox runner (currently no separate runner; Docker preflight only).
4. Application versus policy authority (currently in-process, not independent).
5. Application versus audit storage (currently local JSONL, not WORM).
6. CI runner versus private repository secrets.

## Threat scenarios

- LLM-generated code attempts network access, filesystem writes, resource exhaustion, or privilege escalation.
- Agent messages or memory attempt to smuggle permissions or secrets.
- Approval token theft, replay, expiry bypass, or proposal substitution.
- Audit row modification, deletion, truncation, or complete file replacement.
- Agent attempts to modify policy, kill switch, or child scopes.
- API credential theft, brute force, CSRF, or unauthorized administrative action.
- Container/runtime escape or malicious image/dependency.

## Current mitigations and residual risks

Local HMAC tokens, SQLite nonce uniqueness, deny-by-default role scopes, child-scope intersection, API bearer authentication, Docker preflight, resource-limited Docker invocation, and local audit hash verification are implemented in the prototype. They are not equivalent to independent infrastructure. The API uses a static bearer secret; there is no JWT/session, rate limiting, CSRF control, external OPA, WORM audit, external watchdog, remote runner, or production database.

The source code is generated by an LLM, not assumed to be directly supplied by a hostile human. This reduces some direct-hostile-user scenarios in the intended personal workflow but does not remove prompt injection, dependency compromise, unsafe generated code, or operator error. Treat all generated code as untrusted.

## Required future controls

Separate runner host; gVisor/Firecracker where supported; external policy service; append-only database role plus object-lock retention; independent watchdog; signed reproducible artifacts; short-lived user sessions; rate limits; CSRF protection; secret rotation; SBOM and dependency scanning; chaos and penetration testing.
